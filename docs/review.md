# Permissions and workflow review

Reviewed on 15 November 2026 after the team's feedback about registration cancellation and password visibility. Scope: authentication, every protected API route, academic records, course enrollment/assignment, schedule and registration state, evaluation/publication, reports, shared forms, role navigation, local startup, documentation and tests.

## Policy authority

The user's clarified rule takes precedence over the report's later example `DELETE /registrations` endpoint, which had listed Student. Students register and view their own registrations; the examination office controls cancellation and restoration. The earlier implementation followed that example too broadly.

For official result corrections, the examination office now withdraws publication with a reason. Assigned faculty still own marks, boundaries, generation and publication, as required by FR-018–025. This restriction on withdrawal is a recorded conservative workflow decision, not a claim that the SRS explicitly assigns it. Faculty must ask the office to unlock published results.

`shared/permissions.ts` defines role capabilities; route and domain checks enforce them. A role check does not replace enrollment, ownership, account status or examination-state validation.

## Findings and corrections

| Finding                                                                          | Correction                                                                                                                                                                    | Regression evidence                                                  |
| -------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------- |
| Student could cancel a registration through both UI and API                      | Cancellation is examination-office-only, requires a recorded reason and cannot run after the exam starts                                                                      | API matrix, cancellation API/domain tests, browser cancellation flow |
| Student could restore an office-cancelled registration                           | Student is blocked and directed to the office; office restoration retains the original identifier/seat                                                                        | API and browser tests                                                |
| Login and account password fields had no visibility control                      | Accessible show/hide button, masked by default; does not submit the form                                                                                                      | Login and system administrator browser tests                         |
| Schedule state could be changed without preserving dependent records             | Registrations block return to draft and changes of course/exam type; cancellation closes registrations; cancelled schedules are terminal; evaluated exams cannot be cancelled | Schedule lifecycle tests                                             |
| Past/new schedules and overlapping exams could be created                        | Future time required for new/rescheduled exams; published exams check venue, faculty and shared student conflicts                                                             | Conflict/lifecycle tests                                             |
| Faculty reassignment or enrollment could create a new conflict                   | Recheck published upcoming schedules when assigning faculty or enrolling a student                                                                                            | Domain validation and conflict tests                                 |
| Grading services accepted non-cancelled schedules without a completed-exam check | Marks, boundary edits, generation and publication require a completed published schedule                                                                                      | Domain state tests and disabled UI controls                          |
| Publication could be withdrawn without a correction reason                       | Office-only withdrawal with actor/reason/time; marks remain locked for faculty                                                                                                | API matrix, withdrawal tests, faculty browser flow                   |
| Some domain mutators relied only on route role checks                            | Explicit service permissions and centralized capabilities                                                                                                                     | Direct service denial tests and 34-operation, five-role API matrix   |
| Independent faculty editors could discard each other's unsaved work              | Preserve dirty editor state during related saves; warn before changing exam/page or closing an edited form                                                                    | Browser independent-save/navigation test                             |
| Clearing a saved mark could silently leave the old mark unchanged                | Blank correction is flagged; save is blocked until a valid mark or absence is entered                                                                                         | Browser mark validation test                                         |
| Stale grades were shown alongside recalculation status                           | Hide invalidated grades from the current preview and block publication until regeneration                                                                                     | Invalidation tests and preview guards                                |
| Changing a student report could briefly show the previous student's data         | Bind loaded data to its request path; clear stale data on error; show loading/error feedback                                                                                  | Failed-report browser test                                           |
| Student home counted any published course result rather than their own           | Count only the student's own published result records                                                                                                                         | Same private-result API used by My results                           |
| Inactive or already-linked accounts were offered for new academic profiles       | Restrict choices to matching active unlinked accounts; retain historical record maintenance separately                                                                        | Server validation and filtered forms                                 |
| Critical controls offered invalid actions or allowed closing during saves        | Lock protected fields/self-deactivation, confirm schedule/access changes, disable repeated submit/close while saving                                                          | Browser account/schedule tests                                       |
| Missing student profile produced “Choose a student”                              | Explain that the examination office must create the profile                                                                                                                   | New-student browser test                                             |
| Empty search results and server errors had weak feedback                         | Empty-table message, safe JSON/network errors, schema/constraint error translation                                                                                            | Browser/API checks                                                   |
| Windows development shutdown could leave child servers occupying ports           | Check ports before launch and stop the complete owned process trees on shutdown                                                                                               | Local occupied-port check                                            |

## Verification and remaining acceptance

See [verification.md](verification.md) for the executed checks. Existing user records are retained; automated acceptance tests use isolated data. No database migration or new product module is introduced.

This review documents the rules that were examined and the failures that were corrected. It does not assert that testing proves the absence of every possible defect. The team should demonstrate the permission matrix, review the correction workflow with the instructor, and confirm any institutional policies beyond the supplied report before using real academic data. SQLite/PostgreSQL migration and production operations remain deferred as originally requested.
